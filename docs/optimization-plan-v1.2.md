# Cline2API 优化方案：以账号管理为主线

制定日期：2026-09-19。规划基线为当前本地 v1.1.0 工作区，包含已经完成的账号管理改版；这些改动尚未发布。本文件是后续实施建议，不代表功能已经实现。

建议顺序：先修正凭据和统计行为，再完善账号状态与后台任务，随后补齐诊断、协议兼容和数据持久化。产品继续面向本机及小团队使用，保留 Go 单程序、内嵌管理页和 Docker 两种运行方式。先以 100 / 1,000 个账号做验证；更大规模的设计由压测结果决定。

## 1. 对标结果与取舍

参考仓库 [james-6-23/codex2api](https://github.com/james-6-23/codex2api/tree/de41a5e3dfe9ff51524af864532c42e37955346f)，核对时远端 HEAD 为 `de41a5e3dfe9ff51524af864532c42e37955346f`。以下是源码能力对照，未运行参考项目的线上服务。

| 对标能力 | 当前 Cline2API | 建议 |
| --- | --- | --- |
| 卡片、列表、筛选、批量结果、详情面板 | 已具备第一版，账号页资源已拆分 | 保留现有界面，补齐状态含义、快捷入口和真实浏览器验证 |
| 服务端分页、统计快照、可见账号实时计数 | 全量返回账号，浏览器筛选与分页 | 增加分页接口，将静态资料、用量汇总、运行状态分开读取 |
| 账号启用开关、标签、优先级等配置 | 只有订阅分类和 active/cooldown/expired | 先增加暂停、备注、标签；优先级待运行指标可靠后再做 |
| 批量操作分类结果、后台工作生命周期管理 | 浏览器逐条请求；刷新页面会丢失进度 | 借鉴逐项反馈，独立设计可查询、可取消、可追踪的服务端任务 |
| 近期请求成败条、健康与调度信息 | 累计用量、冷却截止时间、临时测试结果 | 先提供有来源的成功率、错误类型和时间线，再评估健康评分 |
| OAuth 刷新互斥与轮换凭据保护 | 同一账号可能重复刷新；刷新错误统一判过期 | 单进程按凭据归属合并刷新，并确保新凭据可靠保存 |
| API Key 生命周期和用量展示 | Key 字符串及 Free/Pass 授权 | 后续增加名称、停用、有效期、最后使用和 Key 级用量 |

参考实现：[分页与快照](https://github.com/james-6-23/codex2api/blob/de41a5e3dfe9ff51524af864532c42e37955346f/admin/accounts_paged.go)、[可见账号运行计数](https://github.com/james-6-23/codex2api/blob/de41a5e3dfe9ff51524af864532c42e37955346f/admin/account_live.go)、[操作结果分类](https://github.com/james-6-23/codex2api/blob/de41a5e3dfe9ff51524af864532c42e37955346f/frontend/src/lib/accountOperationResults.ts)、[近期请求成败](https://github.com/james-6-23/codex2api/blob/de41a5e3dfe9ff51524af864532c42e37955346f/admin/account_health.go)、[刷新互斥](https://github.com/james-6-23/codex2api/blob/de41a5e3dfe9ff51524af864532c42e37955346f/auth/oauth_refresh_lock.go)。

参考项目的 Codex 5h/7d 额度、工作区身份和对应调度权重具有上游特征。补充核查已确认：ClinePass 官方后台有 5 小时/自然周/自然月已用百分比接口，官方账户 API 有余额和消费明细，推理文档定义 usage.cost。它们可以列入接入验证，真实账号数值与单位尚待核对；免费模型剩余百分比仍未确认，健康分应标为本地观测。详见 [数据来源核查](cline-data-source-verification.md)。当前阶段不引入多渠道扩张、计费门户或分布式部署；继续使用现有前端和 Go 技术栈。

## 2. 优先修正的行为

这些问题直接影响账号管理结果，优先级高于新增页面。

| 优先级 | 当前证据 | 修改目标 | 验收方式 |
| --- | --- | --- | --- |
| P0 | `admin.go` 批量导入调用刷新接口后，保存的仍是传入的 refreshToken | 上游返回新 refreshToken 时保存新值；未返回才保留原值。单个导入及其他入口一并核对 | 模拟轮换后旧 Token 失效，重启仍能继续刷新；持久化失败不能报告导入成功 |
| P0 | `pool.go:refreshAccountToken` 对所有错误设置 expired | 区分凭据失效、限流、超时、网络错误和上游 5xx；临时故障保留凭据并退避 | 模拟 401、429、503、超时，状态与恢复策略分别正确 |
| P0 | `ensureAccountToken` 解锁后执行刷新，多个请求可并行消耗同一凭据 | 按账号/凭据归属合并刷新；使用凭据版本避免旧结果覆盖新值 | 20 个请求同时遇到过期，只发起一次上游刷新；删除或替换凭据后旧刷新结果不能复活账号 |
| P0 | `testAccount` 调用的转发函数增加 UsageCount 和 LastUsed | 明确 production / probe 来源；测试、恢复探测与真实代理统计分开 | 执行 10 次测试后业务请求计数不变；探测量、时间和实际返回的用量单独记录 |
| P0 | 上游请求未贯穿客户端 context；管理测试可能等待无期限 | 探测有总超时，推理采用连接/响应头/流空闲超时；取消能中止等待和退避 | 模拟上游无响应及客户端断开，任务及时结束且不继续选号重试 |
| P1 | 模型测试从全局默认模型选择，随后固定走 Cline | 按账号所属上游与授权能力挑选测试模型，保存测试模型名称 | 默认模型设为 Zen 时，Cline 账号测试仍使用兼容的 Cline 模型 |

刷新取消要特别处理：普通请求断开可以取消等待；已经开始消耗轮换凭据的刷新，应在独立、有上限的临界区内完成交换与保存。不能因为管理页关闭而丢掉上游刚返回的新 refreshToken。磁盘保存失败时，保留新凭据的受保护内存副本和明确错误，停止后续刷新并允许重试保存；不能声称旧凭据仍然可用。进程崩溃与磁盘同时故障仍是恢复边界。

## 3. 账号管理目标设计

### 3.1 状态和元数据

将互相独立的事实分开存储，再由界面组合展示：

| 维度 | 建议字段/含义 | 规则 |
| --- | --- | --- |
| 运维开关 | `enabled`：启用 / 暂停 | 暂停只禁止新请求调度；已有请求正常收尾。刷新成功、自动恢复不能擅自取消暂停 |
| 订阅分类 | `subscription`：unknown / free / pass | 保持现有 Key 授权边界。独立展示分类来源和最近确认时间 |
| 凭据 | `credentialState`、`lastRefreshAt`、`lastRefreshError` | 凭据失效与网络暂时不可达分开；时间未知时展示未知 |
| 调度可用性 | `availabilityReason`、账号/模型冷却时间 | “活跃”不等于任意模型可用；按目标模型解释不能调度的原因 |
| 运维资料 | `displayName`、`note`、`tags` | 标签只用于组织筛选，不改变 Free/Pass 授权，不承担安全边界 |
| 最近诊断 | `lastProbeAt`、`probeModel`、`probeResult`、`errorClass` | 保留结果和发生时间；结果不能无期限被视为当前健康证明 |
| 运行指标 | 活跃请求、待处理请求、最近成功/失败 | 活跃并发驻留内存，进程重启从零开始，不写回长期统计 |

旧数据中没有 `enabled` 时迁移为 true，需区分“字段缺失”和显式 false。其他新增字段为空时不推测历史数据。支持暂停单个账号与批量暂停；重新启用后仍须通过订阅、凭据及模型冷却检查。

### 3.2 列表和详情

账号卡片保留邮箱/名称、订阅、状态、累计用量三个层级，补充暂停标记、最近错误简述、状态更新时间。管理员优先操作为“详情、测试、暂停”；删除与凭据导出放在明确的管理操作中。

详情侧栏分为概览、模型状态、近期请求、变更记录四部分。支持从某条失败直接跳到对应日志；模型冷却显示原因、截止时间和最近探测结果。编辑中的备注或标签不能被后台轮询覆盖。

真实账号验证通过后，Pass 概览增加三窗口额度条；按量钱包余额和账单另行展示。使用官方 percentUsed/resetsAt，不通过累计 token 推测额度；查询失败或数据缺失不显示为 0%。

增加 URL 中的筛选状态、保留列显示偏好、按状态快捷筛选和键盘访问。选择本页与选择全部筛选结果显示准确数量；排序不应丢失明确选中的 ID，修改筛选条件继续清空选择并提示。界面布局用真实浏览器检查 390 / 768 / 1440px 三档，补齐前一轮尚未完成的视觉验证。

### 3.3 分页与状态更新

新增 `GET /admin/api/accounts/page`，支持 search、subscription、status、enabled、tag、sort、page、pageSize，默认每页 24，最高 100。原 `/accounts` 在迁移期保持兼容。

返回 `items`、`totalFiltered`、`totalAll`、`summary`、`snapshotAt`、`revision`，明确总览是全账号池口径；筛选命中数单独展示。分页按“排序字段 + accountId”稳定排序，使用同一短期快照避免翻页重复或漏行；快照过期时提示刷新。

资料与状态采用不同刷新节奏：列表按操作后刷新，活跃请求与任务进度只查询当前页 ID；页面隐藏或离开账号页时暂停轮询。接收旧请求的响应时检查序号/revision，避免覆盖新筛选结果。批量操作完成后必须排队执行一次最终刷新，不能被已有 `loading` 状态直接丢弃。

先在内存快照上实现分页，降低网络传输和 DOM 工作量；这不会消除后台全池扫描。数据库索引分页放在后续存储阶段，不提前宣称大规模性能提升。

### 3.4 导入与去重

导入改为“预检 → 查看新增/重复/无效项 → 提交 → 查看逐项结果”。预检只解析本地结构，不消耗可能轮换的 refreshToken；只有提交后的验证阶段访问上游。

可确认身份时按上游账号稳定 ID 去重。没有稳定 ID 时对完全相同的凭据做内部指纹去重；邮箱只提示潜在重复，不能据此静默覆盖。默认跳过重复，更新已有凭据需要明确选择，并保留原账号 ID、累计统计和授权设置。导入中新增凭据立即安全保存，避免等整批结束才持久化。

## 4. 服务端批量任务

将测试、刷新及导入验证从浏览器循环迁移到服务端；批量修改分组和删除仍使用短事务，维持“全部验证通过再提交”。凭据导出按请求生成，不将明文导出内容保存在任务结果里。

建议接口：

| 接口 | 行为 |
| --- | --- |
| `POST /admin/api/account-operations` | 接收 action、显式 accountIds 与幂等标识；返回 202 和 operationId |
| `GET /admin/api/account-operations/{id}` | 返回任务进度、逐项结果、开始/结束时间；支持刷新页面后恢复查看 |
| `POST /admin/api/account-operations/{id}/cancel` | 停止排队项；中断可取消的探测；刷新临界区完成保存后退出 |
| `POST /admin/api/account-operations/{id}/retry-failed` | 仅对失败或未执行项创建新任务，保留原始结果 |

第一版建议默认全局最多 3 个测试/刷新工作项并发，同一账号最多 1 个；这是待验证的保守起点，应可配置。重叠任务共享同一限额，管理任务的上游调用也计入上游并发预算。排队有容量上限与超时，防止大量批量请求堆积。

目标账号在创建任务时固定成 ID 快照，界面筛选改变不影响已启动任务。执行前再次检查账号是否存在、操作者是否仍具备管理员权限。任务状态至少区分 queued、running、cancelling、completed、cancelled、interrupted；失败情况按 success/failed/skipped/cancelled 数量报告，不能只给绿色“完成”。

页面关闭后任务继续；进程重启后残留 running 标为 interrupted，不自动重放。尤其刷新请求在中断时是否已消耗凭据可能未知，必须先核对本地已保存版本。任务记录包含操作者、action、账号 ID 和脱敏结果，保留周期可配置。

最初可用独立原子 JSON 文件保存有界任务记录；引入存储接口后再迁到 SQLite。首版继续保留单次最多 1000 个账号的边界。

## 5. 配套的可靠性、观测和存储

### 5.1 调度与协议

- 统一请求上下文、结构化错误分类、重试预算和使用量记录；三个协议入口共用这些能力。
- Cline 选择账号时检查启用状态、Key 授权、凭据、模型冷却和单账号并发；释放并发名额要覆盖流结束、读取失败、客户端取消与 Body.Close。
- Zen 当前并发名额在返回响应头时释放，未覆盖完整流寿命。修正为完整响应周期，并让等待名额与退避可取消。
- 先展示“为什么选择/排除某账号”；健康调度先以影子模式观察建议与现有轮询的差别，经验证后再可选启用。初期不复制参考项目的固定评分权重。
- Responses 使用每个 tool call 独立的累积器，保留并行参数和最终 output；正常结束、异常截断和取消使用不同终态。Chat 流同样不能将所有 EOF/读取错误直接记成成功。
- 热切换监听地址先验证目标可绑定，再迁移服务；失败时恢复旧监听，不能只在日志里报错而留下不可访问的后台。

### 5.2 可观测性与 API Key

日志增加请求 ID、业务/探测来源、请求模型/实际模型、Key ID、错误类别和重试次数；多次上游尝试与一次客户端请求分别计数，避免账号降级让成功率失真。

先做账号近 24 小时成功率、失败原因分布、TTFT 和近期成败条。明确统计样本数、覆盖起止时间和时区；无请求时显示“暂无样本”。当前日志只保留最多 5000 条或 30 天，不能把截断后的数据伪装成完整的 30 天统计。

Key 后续增加名称、停用、到期时间、最后使用及请求/并发限制。计数关联稳定 Key ID，日志不写原始 Key。新 Key 只在创建时显示明文，旧 Key 通过迁移映射保持可用。

现有普通后台用户可查看全部账号元数据；这是只读运维角色。若需要客户隔离，必须单独设计数据归属与授权查询，不能仅靠页面隐藏。先补管理员操作审计及登录速率限制。

### 5.3 存储与代码组织

将账号资料、凭据更新、用量、日志、任务分别通过 Store 接口读写。当前账号选择和用量更新频繁在全局锁内重写完整 JSON，日志每条追加也会排序并重写全部保留项；原子保存解决了文件完整性，但没有解决写入量和锁等待。

单机长期运行优先评估 SQLite：凭据、用户、Key 与运维配置使用事务立即提交；日志和统计采用有界队列/批次，并明确刷盘周期与异常退出的丢失边界。是否引入 SQLite 以基准测试和功能依赖决定；首版不依赖 PostgreSQL 或 Redis。

按变更逐步抽离 `internal/accounts`、`internal/operations`、`internal/upstream`、`internal/protocol`、`internal/store`，入口保持薄层。前端沿用现有 `web/` 模块，将接口请求、通知、表单和翻译逐步复用。不要在同一阶段同时重写协议、存储和整个前端。

## 6. 建议版本与交付门槛

以下版本号是建议，不改变当前 v1.1.0 标识。

| 阶段 | 建议版本 | 本阶段交付 | 必须通过的验收 |
| --- | --- | --- | --- |
| A：准确性与恢复 | v1.1.1 | 轮换凭据保存、刷新合并、错误分类、测试统计隔离、探测超时 | 故障注入下不把临时错误判永久失效；并发只刷新一次；探测不增加业务计数；新凭据重启可用 |
| B：账号管理 | v1.2.0 | 启用/暂停、备注/标签、服务端分页、导入预检去重、服务端批量任务、界面验收 | 暂停不被自动刷新撤销；重复导入不增加账号；刷新页面找回任务；取消不再启动后续项；操作目标不漂移 |
| C：诊断与协议 | v1.2.1 | 完整流并发约束、错误时间线、准确统计、Responses 并行工具及失败终态 | 长流实际并发不超限；客户端断开后连接释放；一次请求与多次尝试不混算；三协议回归通过 |
| D：长期运行 | v1.3.0，按需求推进 | 持久化优化、API Key 生命周期、审计、按需健康调度 | 迁移数据核对一致；已停用/过期 Key 立即拒绝；健康策略有可解释证据；性能和恢复测试达标 |

验收数据包含 100 和 1,000 个演示账号、多模型冷却、失效凭据、慢上游、乱序响应和中途断流。性能目标可先设为：单机本地、1000 账号、每页 24 条时，列表接口 p95 ≤ 300ms；测试环境和账号规模需随报告记录，不能当成已实现结果。大规模优化前先留存当前版本基线。

每阶段都要求 Go 测试、竞态检测、相关前端逻辑测试，以及账号页真实浏览器交互/布局验收。外部真实账号只用于经用户授权的少量连通性验证，自动回归使用模拟上游。Windows/Linux 桌面和 Docker 由对应环境测试，不能由 Mac 编译通过替代。

## 7. 第一批建议实施清单

推荐先单独完成 A 阶段，形成可回归验证的小版本：

1. 统一手动添加、批量导入、SSO/OAuth 入口的凭据保存规则，优先保留上游轮换后的 refreshToken，保存失败显式报错。
2. 定义认证失效、限流、网络、超时、上游错误和本地存储错误，停止把所有刷新错误标成 expired。
